# 契約の形を決める作業の手順書

## 目的と適用範囲

- 公開の契約に対応する操作・型がまだ無い項目について、形（操作・型・エラー・能力の問合せ）を決める作業の進め方を定める。
- 作業は 2 段で進める。「形を決める」タスクで決定を記録し、「決めた形を実装し、確かめる」タスクで実装・公開テスト・公開の明文を揃える。
- 前提: spec の TASK-2 と TASK-3（ポインタ表記）、および [spec-confidentiality](../../.claude/rules/spec-confidentiality.md)。

## 置き場の全体像

| 置くもの | 置き場 |
| -------- | ------ |
| 振る舞いの正 | `docs/spec/04-behavior/`（private） |
| 決定の記録 | private spec 側（該当タスクの決定の記載と、該当項目） |
| 生成物 `spec.md` | 手書きしない。public に出さない |
| 公開の契約の明文 | 公開 API の rustdoc と `docs/contract/<領域>.md`（実装・公開テストと同じ PR で書く） |

本リポ（public）に置かないもの: 決定の理由・代替案・オーナーの判断の経緯・未実装の予定・計測値・実ホスト名・資格情報。

## 決定の記録の書式

記録は private spec 側に置く。必須項目は次のとおり。本リポ（`docs/contract/`）に置く分（公開してよい欄だけ）の雛形は [TEMPLATE](TEMPLATE.md) で、下の表の全部の欄を持つ雛形ではない。

| 項目 | 内容 |
| ---- | ---- |
| 対象 | 項目 ID（ポインタ表記） |
| 提供する背後実装 | Metal / Vulkan / CUDA / CPU のうち提供するもの |
| 提供しない背後実装 | 能力の問合せが返すもの。暗黙のフォールバックはしない |
| エラーの形 | 共通のエラー型への写像。backend のエラーコードを握りつぶさない |
| 操作・型の案 | 公開する操作と型 |
| `04-behavior/` の更新案 | 更新する項目の ID |
| オーナーの判断 | 要否と、得た日付 |

## 手順

1. 着手前の確認（Claude Code）: 前提タスクの状態、対象の項目 ID、既存の公開 API・能力の問合せとの関係を確かめる。
2. 案の作成（Claude Code）: 背後実装ごとの提供の有無・能力の問合せ・エラーの形の観点で、選択肢・影響・推奨を整理する。
3. オーナーへの伺い（Claude Code → オーナー）: 伺う対象・提示する情報・経路・公開側に書かないことは [contract-shaping-escalation](../../.claude/rules/contract-shaping-escalation.md) に従う。回答を得るまで、その点は決めずに止める。
4. 振る舞いの正を先に更新する（spec リポ側）: `04-behavior/` → タスクの記載 → `spec.md` の生成の順に追随させる。本リポからは spec を書き換えず、spec リポ側の作業としてユーザーに依頼・報告する。
5. 決定の記録を spec 側に残す（書式は前節）。
6. 「実装し、確かめる」タスクへ引き継ぐ: 実装・公開テストと同じ PR で rustdoc と `docs/contract/<領域>.md` を書く。条件は次のとおり。
    - テストで確かめられた、実在する振る舞いだけを書く。
    - コードとテストから説明し、spec の文を写さない。
    - spec との対応は `04-behavior/` の項目 ID のポインタだけにする。
    - 項目 ID の一覧・件数・索引は作らない。
7. 不足・矛盾が見つかったとき: ビヘイビアの不足・矛盾や PoC の不足を見つけても、`04-behavior/` や前フェーズの文書を黙って書き換えない。本リポのコード・文書で先取りもしない。所在を ID のポインタで示し、前のフェーズへの差し戻しを提案して spec 側の課題としてユーザーに報告し、該当する形を決める作業は保留する。
