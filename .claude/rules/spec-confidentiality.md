# private spec の機密保持規約（リポ固有・P0）

## 前提

- 本リポジトリは **public**
- 仕様・フェーズ文書の SSOT は **private** リポジトリ `Fandhe-AI/fandhe-silicon-spec`（`docs/spec` submodule。`update = none`）にあり、**意図的に非公開を維持**する

## 禁止事項

以下を public な資産（コード・コメント・ドキュメント・Issue・PR 本文・コミットメッセージ）へ持ち込まない:

- spec 本文の長文引用・ファイルコピー
- 非公開の内部判断・設計議論の転記
- spec の構成・内容を実質的に復元できる要約

## 許可される参照（ポインタ表記）

- spec 内のファイルパス（例: `docs/spec/<dir>/<file>.md`）
- タスク ID・ビヘイビア ID・フェーズ ID 等の識別子
- 1〜2 行程度の、README で**既にオーナーが公開済みの範囲**に収まる要約

## 例外: 公開 API の振る舞いの契約（spec TASK-2・TASK-45 の決定）

契約の明文（振る舞い）は public 側（本リポ）に置くとオーナーが決定した（spec の TASK-2・TASK-45、
2026-10-11 記録）。ただし公開してよいのは、**本リポに既に存在する公開 API が、利用者に約束する振る舞い**に限る。
上記の禁止事項（復元可能な要約の禁止を含む）は、この範囲の外では引き続きすべて適用する。

### 公開してよい範囲（すべてを満たすこと）

- **対象**: 同じ PR または既にマージ済みのコードで public になっている API 項目（型・関数・trait・能力の問合せ結果）だけ。
  まだ本リポのコードに無い項目・予定・未実装の契約は書かない
- **内容**: その項目について利用者が依存してよい約束だけ。具体的には、前提条件と入力の検証規則、返すエラーの種類と
  発生時点、安全性・同期・メモリ可視性の保証、デバイスロスト時の扱い、能力の問合せが返す値の意味
- **書き方**: 公開 API の rustdoc（と、その rustdoc を束ねる本リポの契約の文書。パスは spec TASK-3 の手順で確定）に、
  コードの説明として書く。spec の節・表・文の単位での書き写しや言い換えはしない
- **対応づけ**: 各記述に `04-behavior/` の項目 ID を 1 つ以上ポインタとして付ける（決定・変更の正は引き続き `04-behavior/`）

### 例外の対象外（引き続き禁止）

- 公開 API 項目に結び付かない記述。`04-behavior/` のファイル・節・表の構成、項目 ID の一覧や範囲・件数の集計、
  複数項目をまたぐ要約・索引（項目ごとの記述を集めて spec を復元できる形にするもの）
- 優先度（Must / Should 等）・確定 / 検討中などの状態・理由や代替案・議論の経緯・オーナーとのやりとり
- PoC・計測の記録と数値、ロードマップ・マイルストーン・タスク（`05-tasks.md`・`06-roadmap.md` 等）、`spec.md`（生成物）
- 実ホスト名・非公開の接続先・秘密情報・機材や課金の情報

公開してよいか迷う場合は、この例外を適用せず、転記しない側に倒してユーザーに確認する。レビュー（reviewer /
security-auditor / codex）では、上記の範囲の外の記述を従来どおり P0 として扱う。

## 運用

- 公開可否に迷った場合は**転記しない側**に倒し、ユーザーに確認する
- subagent への指示・subagent からの報告でも同じ規約を適用する（報告が PR 等へ転記されうるため）
- レビュー時（reviewer / security-auditor）は spec 漏えいを P0 として検査する

## コミットメッセージ・PR 本文での運用

- コミットメッセージ（件名・本文）・PR 本文・レビュー返信も public 資産であり、上記の禁止事項・ポインタ表記が同様に適用される
- squash merge 後もブランチ上の中間コミットは GitHub の PR refs（`refs/pull/<n>/head`）から参照可能であり、
  main の history rewrite では除去できない。**マージ前の検査で防ぐ**ことを原則とする
- レビュー指摘（spec 転記）への対応コミットでは、「何を削除したか」の説明に spec の内容を再転記しない。
  「private spec 由来の記述を削除（ID のポインタのみ残置）」のように ID ポインタと削除の事実だけを書く
- PR 作成時（create-pr スキル実行時）に `git log <base>..HEAD --format="%H %s%n%b"` で base から HEAD までの
  **すべての中間コミット**の件名・本文を検査し、禁止事項への抵触が無いことを確認する。抵触を検出した場合は
  ポインタ表記へ書き換えて解消するまで**マージを停止**する
- マージ後に発見した場合は Issue で扱いを決め、history rewrite は原則行わない
