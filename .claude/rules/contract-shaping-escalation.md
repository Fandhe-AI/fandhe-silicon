# 契約の形を決める作業でのオーナー判断の伺い方・spec 側への差し戻し

## 目的・適用範囲

private spec の TASK-3（`docs/spec/05-tasks.md`）を前提タスクに引く「形を決める」作業を本リポで進めるときに適用する。
決定の記録の置き場・書式、ビヘイビア先行の更新順は本規約の対象外（別の規約・手順書で扱う）。

## 共通原則

- 自己承認しない。承認の有無を事実以上に書かない（作業の summary・private 側の記録・ユーザーへの報告）
- 公開側（PR 本文・コミットメッセージ・Issue・文書・コード内コメント・レビュー返信）には、private spec 側の状態（判断待ち・保留・承認の有無・伺いの番号や中身・日付。定義は [spec-confidentiality](./spec-confidentiality.md)）を書かない。書けるのは ID のポインタと「private spec 側の記録に従う（ポインタのみ）」の 1 行まで。依存の承認の記録（`deps-approved.toml`）は承認の記録を公開側に持つ仕組みなので別で、[dependency-policy](./dependency-policy.md) に従う
- `docs/spec` 配下（`04-behavior/` を含む）を本リポのブランチから書き換えない。submodule のポインタも独断で進めない（更新は `update-external.yml` の PR 経由）
- public 資産へ spec の本文・内部判断の経緯を書かない（[spec-confidentiality](./spec-confidentiality.md)）。参照は ID・パスのポインタに限る
- 判断が付かないときは止めて報告する（fail-closed）。推奨案を黙って確定しない

## オーナー判断の伺い方

### 伺う対象

| 区分 | 例 |
| ---- | -- |
| 伺う | 既存の決定から一意に導けない選択（どの背後実装で提供するか・非提供の背後実装で能力問合せが何を返すか・エラーの形など複数案が並ぶもの）、優先度・範囲の変更、既存の決定と異なる向きを採る場合 |
| 依存承認へ委ねる | 依存の追加・更新（[dependency-policy](./dependency-policy.md) の承認フロー） |
| 伺わずに決めてよい | 既存の決定から一意に導けるもの（根拠を ID ポインタで記録する） |

### 1 論点ごとに提示する情報

1. 論点の 1〜2 行の要約と、対象の項目 ID・タスク ID（ポインタ）
2. 選択肢（原則 2〜3 案）と各案の影響（背後実装ごとの提供可否・能力問合せの返り値・エラーの形・上位ライブラリへの影響・工数）
3. 推奨案とその理由
4. 決まらないと止まるもの（ブロックされるタスク・項目）
5. 「推奨で」の一言で答えられる回答の形

同じタスクの論点は番号を付けて 1 回にまとめて伺う。Go/No-Go の判定とは区別して書く。これらの情報は作業の summary（main セッションへの報告）に残し、main セッションがユーザーに伺う。公開側には書かない。

### 経路

- 対話セッション: ユーザーへ直接伺う
- 自動運転で質問できない場合: 当該論点の形決めを止め、上の情報を作業の summary に残す（PR 本文に「オーナー判断待ち」節を置かない）。推奨案を既定として先行確定しない。仮置きする場合は、判断が出るまでマージしない。仮置きである旨と伺いの中身は summary に残し、公開側には書かない
- ラベルの新設・Issue の起票は承認なしに行わない（[out-of-scope-tracking](./out-of-scope-tracking.md)）
- 回答の spec 側への記録は spec リポ側の作業とし、本リポからは書き換えない

## spec 側への差し戻しの提案手順

### 検出の対象

- 不足: 形を決めるのに要る振る舞いが `04-behavior/` の項目に無い
- 矛盾: 項目どうし、項目と既存の決定、項目と実機・実装の挙動が食い違う
- PoC の不足: 判断材料となる実測・確認が無い

### してはいけないこと

- `docs/spec` 配下の文書を本リポ側から書き換える
- 矛盾を rustdoc・契約の文書・テストで黙ってどちらかに寄せる（テストの無い約束は書かない）
- テストの期待値を弱めて辻褄を合わせる

### 手順

1. 該当する項目の形決めだけを止める。影響しない項目は続けてよい
2. 提案をまとめる。種別、該当の項目 ID・タスク ID・spec 内パス（ポインタ）、本リポのコード・テスト・実測で示せる事実、提案（追加・修正案、PoC の追加案）、止まるタスクを含め、形式は上の提示情報に揃える
3. spec リポ側の課題としてユーザーへ報告する（[out-of-scope-tracking](./out-of-scope-tracking.md) の spec 側変更の経路）。本リポの public な Issue・PR には ID のポインタだけを書く（状態は書かない）
4. 決まるまで、当該項目の形決めを止める。止めている事実は summary に残し、公開側には書かない
5. spec 側の更新が submodule 経由で取り込まれてから再開する

本リポから出すのは更新の案までで、更新自体は行わない。
